# Native Playback — plan

Status: Ready
Created: 2026-08-03
Updated: 2026-08-03

> Part of the [Apple client](../apple-client/plan.md) epic, and the second half of
> the server surface. [`native-client-api`](../native-client-api/plan.md) ends where
> the client can browse; this feature makes it play. It was carved out of that plan
> because the two together were one unreviewable PR.
>
> It defines *what is served and to whom*. **How a file is repackaged when the
> client cannot open it is `remux-streaming`** — this plan holds the contract that
> feature plugs into and ships without it.

## Goal

Decide what a given client can actually play, let it choose deliberately among
editions and tracks, remember that choice across devices, and record what was
watched through the same path every other client already writes.

## Target behavior

### Playback resolution

`POST /native/v1/playback/resolve` takes the client's **capability profile** —
containers, video and audio codecs, HDR formats, channel layouts, passthrough — and
answers per media source with one of:

- `directPlay` — the original file, served by byte range, the existing
  direct-stream path;
- `remux` — a URL for the same streams repackaged into a container the client can
  open. **What that container is, and how it is delivered, belongs to
  `remux-streaming` and deliberately not to this contract**: the client follows a
  URL either way, so a change of packaging must never be a change of API;
- `unsupported` — with a machine-readable reason, so the client can say "this
  copy's only audio track is DTS" rather than failing silently.

This replaces the Jellyfin surface's `EnableDirectPlay`/`EnableDirectStream` flags,
which that surface parses and then ignores because it has only one answer to give.
Until packaging lands, `remux` is simply never returned, and the contract does not
change when it starts being.

**Resolution is also what decides which signalling a client is served**, which the
[spike](../apple-client/plan.md#the-answer-drop-hls) proved is not cosmetic: a
Dolby Vision `dvh1` sample entry engages DV on a device that supports it and breaks
one that does not, while the cross-compatible `hvc1` + `dvvC` form reads as HDR10
everywhere. **Dolby Vision therefore cannot be served to anyone until this endpoint
exists to ask** — an ordering constraint on the whole epic, recorded here because
this is where it is enforced.

### Track preferences

A per-user preference, scoped globally, per series, or per item: preferred audio
language, preferred subtitle language, forced-only, and "prefer original audio".

Stored as **intent, never stream indexes** — an index means nothing across two
editions of the same film, and the client resolves intent against whatever the
chosen source actually holds. Preferences ride the sync feed
([`native-client-api`](../native-client-api/plan.md#delta-sync)) as their own
entity type, so choosing the Russian dub for a show on the Apple TV holds on the
iPhone.

### Playback sessions

Start / progress / stop, carrying the media source, the selected audio and subtitle
streams (including external sidecars), and the device.

They write through **`UserDataService`**, the same path the Jellyfin surface uses —
no second writer. That is what keeps the watched threshold, the resume rules, the
season and series aggregates, `PlaybackHistoryEntries`, and the Trakt outbox
identical no matter which client played the file.

## Deliverables

One PR.

- [ ] **`POST /native/v1/playback/resolve`** with the capability profile and the
      three answers, including which signalling each client is offered.
- [ ] **Preference entity + endpoints**, resolved as intent against a source, and
      emitted into the change log so they sync.
- [ ] **Session endpoints** (`start` / `progress` / `stop`) writing through
      `UserDataService`.
- [ ] **OpenAPI coverage** for the routes this feature adds, generated by the same
      step `native-client-api` wires up.
- [ ] **Unit tests**: resolution across capability profiles including the DTS-only
      source and a client that does and does not report DV support; preference
      resolution against two editions with different track layouts; and session
      writes producing user-data and history rows indistinguishable from the ones
      the Jellyfin path produces for the same play.

## Settled before Ready

- **Whether resolution knows the packager's readiness** — decided: `remux` is
  returned **only when the server reports packaging as available**, which
  `GET /native/v1/server` already answers. What happens between the answer and the
  first byte — cold start, queueing, cancellation — belongs to `remux-streaming`
  and is deliberately invisible here: the client follows a URL, and this contract
  does not describe how that URL becomes ready.
- **How much of the capability profile to model** — decided: the four axes the
  spike showed actually matter — **container, HDR form, audio codec, passthrough**
  — and nothing else in v1. The profile is a request body, not a stored entity, so
  adding an axis later is additive and costs no migration. A coarse device class is
  rejected: it ages badly and cannot express the one distinction the spike proved
  is real, which is whether a client engages Dolby Vision.
- **Sidecar audio at playback time** — decided for v1: the resolution response
  says nothing about sidecars, and a client fetches them as separate files. If
  `remux-streaming` later folds them into its output, the response gains a field
  saying so; that is additive and does not block this feature.

## Accepted residual risks

- A client that misreports its capabilities gets media it cannot play. There is no
  server-side verification of a capability profile, and inventing one would be
  guesswork about a device the server cannot see.
- Serving `dvh1` to a client that claimed Dolby Vision support and does not have it
  fails at the device, not at the API. That is the cost of trusting the profile,
  and the fallback is the cross-compatible form, which the user can force.

## Verification steps

1. `dotnet test` for the API test project.
2. Resolve playback for an MP4 (direct), an MKV (`remux`, or `unsupported` until
   packaging lands), and a DTS-only source (`unsupported`, with a reason).
3. Resolve the same Dolby Vision source for a client reporting DV support and one
   that does not, and confirm the two are offered different signalling.
4. Play through the native session endpoints and confirm the resulting
   `UserItemData` and `PlaybackHistoryEntry` rows are indistinguishable from the
   ones Infuse produces for the same play.
5. Set a track preference on one device and confirm it arrives on another through
   the sync feed.
6. Confirm Infuse still plays and syncs state throughout — the Jellyfin surface
   must not regress.
